# Tektronix FCA3003

Driver standardowej biblioteki Python, bez VISA i pip:
[`FCA3003`](../labinstruments/fca3003.py), profil `fca3003` w istniejącym
`Driver`, CLI oraz opcjonalnym serwerze `control`. Raspberry Pi wykonuje USBTMC;
host może korzystać z transportu bramki HTTPS. Driver nie wymaga instalowania
sterownika producenta. Wymagany tryb SCPI **NATive**, nie COMPatible.

## Użycie na Raspberry Pi

```sh
python3 -m labinstruments usb-list
python3 -m labinstruments identify --model fca3003 --usb-serial NUMER_USB
python3 -m labinstruments read --model fca3003 --usb-serial NUMER_USB \
  --operation frequency --channel 1
```

Numer USB pochodzi z `usb-list`; może różnić się od numeru odpowiedzi `*IDN?`.
Opcja `--serial` sprawdza numer SCPI. Nie zapisuj `/dev/usbtmc0` w konfiguracji:
numer węzła zmienia się po podłączeniu urządzeń.

```python
from labinstruments.transport import Transport
from labinstruments.fca3003 import FCA3003

with Transport({'kind': 'usb', 'serial': 'NUMER_USB', 'timeout': 4}) as io:
    counter = FCA3003(io, serial='NUMER_SCPI')
    print(counter.identify())
    print(counter.measure('frequency', 1))                    # Hz, input A
    print(counter.measure('frequency', 3))                    # Hz, input C
    print(counter.measure('period', 2))                       # s, input B
    print(counter.measure('frequency_ratio', 1, second_channel=2))
    print(counter.measure('frequency', 6))                    # internal reference
```

`measure()` zwraca `float`; `measure_raw()` zachowuje tekst SCPI po sprawdzeniu
wyniku. `Driver(io, 'fca3003').read(operation, channel)` zwraca ten sam tekst,
z ustawieniami domyślnymi, dla kanałów fizycznych 1–3. Klasa `FCA3003` pozwala też
mierzyć częstotliwość wejścia arming (4) oraz wewnętrznej referencji (6).

| Operacja | Jednostka | Kanały |
|---|---|---|
| `frequency` | Hz | A=1, B=2, C=3; klasa FCA3003 także 4/6 |
| `period`, `period_average` | s | 1, 2, 3 |
| `positive_width`, `negative_width`, `rise_time`, `fall_time` | s | 1, 2 |
| `duty_cycle`, `negative_duty_cycle` | ułamek, 0.5 = 50% | 1, 2 |
| `vpp`, `voltage_max`, `voltage_min` | V | 1, 2 |
| `frequency_ratio` | iloraz | para kanałów 1, 2, 3 |
| `phase` | stopnie | para kanałów 1, 2 |
| `time_interval` | s | para kanałów 1, 2 |

Drugi kanał pary można podać przez `second_channel`; domyślnie jest to 2 dla
kanału 1 i 1 dla pozostałych. Input C jest wejściem RF do 3 GHz; nie oferuje
ustawień triggera i pomiarów napięcia dostępnych na A/B. Nie zaimplementowano
tablic, timestampów, trybu totalize, zapisów do pamięci ani całego zestawu SCPI.

## Stan przyrządu i obsługa błędów

Każdy pomiar przerywa poprzednią akwizycję i wykonuje `CONF:<funkcja>`.
Według instrukcji Tektroniksa konfiguracja przywraca nastawy wejść, sense i triggera
do wartości resetowych. Driver następnie ustawia ASCII, wyłącza timestampy,
ustawia aperture i timeout, po czym wykonuje `READ?`. Nie przywraca poprzedniej
konfiguracji. Nie używaj go równolegle z innym klientem lub pomiarem panelowym.

Nie stosujemy `MEAS?`: ta komenda ponownie konfiguruje urządzenie, tracąc wcześniej
ustawiony timeout. Domyślna aperture wynosi 0.1 s, timeout przyrządu 1 s;
można je podać jako `aperture` i `measurement_timeout`. Timeout transportu musi
być większy o ponad 0.5 s. Aperture nie jest czasem uśredniania dla każdej funkcji,
np. `period` mierzy jeden okres, a `period_average` uśrednia.

Przed konfiguracją driver weryfikuje model, opcjonalny serial, native mode oraz
istniejący błąd SCPI. Nie wysyła `*CLS`. `error()` pobiera jeden wpis kolejki;
`check_error()` zgłasza `InstrumentError` dla kodu innego niż zero. Driver czyta
i kasuje zdarzenia `STAT:QUES?` przed pomiarem, a następnie sprawdza nowe zdarzenia:
timeout (1024) zgłasza `TimeoutError`; overflow, calibration error, out-of-limit
i unexpected parameter zgłaszają `InstrumentError`. NaN/Inf, wielkie wartości
zastępcze (|x| ≥ 1e30) i odpowiedzi inne niż pojedyncza liczba są odrzucane.

Błąd transportu nie powoduje ponowienia komendy. Po takim błędzie sprawdź stan
urządzenia i zaległe odpowiedzi przed kolejną akwizycją. `abort()` przerywa pomiar,
ale nie usuwa zaległej odpowiedzi z USB/TCP.

## Zdalny transport

Jeśli RPi uruchamia bramkę z tego repo, użyj konfiguracji `gateway` z jej
rzeczywistymi `url`, `slot`, `ca_file` i `token_file`, opisanej w
[deploy/README.md](../deploy/README.md). Klasa FCA3003 nie zależy od transportu.
Istnienie starego serwera TMDSusb nie oznacza obsługi tego API HTTPS;
protokół działającego serwera należy potwierdzić przed podaniem konfiguracji.
Alternatywa: uruchomienie skryptu pomiarowego bezpośrednio na RPi przez SSH.

## Weryfikacja

```sh
python3 -m unittest discover -s tests -v
python3 scripts/hil-fca3003.py --usb-serial NUMER_USB --serial NUMER_SCPI \
  --output /tmp/fca3003-hil.json
```

Skrypt HIL wykonuje trzy rzeczywiste pomiary wewnętrznej referencji (kanał 6),
domyślnie porównując je z 10 MHz. Nie jest to kalibracja: pomiar używa tej samej
referencji co licznik. Test wejścia wymaga podania kanału i znanej częstotliwości:
`--channel 1 --expected-hz 1000000`. Skrypt nie włącza generatorów ani innych źródeł.
Transport bramki można podać przez `--transport-json /path/transport.json`.
Raport zapisuje rzeczywiste wyniki i `simulated: false`; nie zapisuje tokenów.

Testy programowe sprawdzają kolejność konfiguracji, kanały i jednostki, błędną
tożsamość, brak sygnału, status i kolejkę błędów oraz brak ponowień po błędzie I/O.
Próba fizyczna **NOT_RUN**: znaleziono RPi przez mDNS, ale brak danych logowania
i potwierdzonego protokołu TMDSusb. Nie wysłano komend do przyrządu.
[Raport zakresu weryfikacji](../reports/fca3003-2026-10-09/status.json).

Źródło komend: [Tektronix Programmer Manual 077049400, Rev A](https://download.tek.com/manual/077049400webRevA_0.pdf).
